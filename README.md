## 1. 프로젝트 소개

**TONE**은 정해진 질문에 답하면 8가지 성향 컬러 유형(설계자형·도전가형·리더형·탐험가형·분석가형·몽상가형·중재자형·조력자형) 중 하나를 진단해주는 서비스입니다. 유형 자체는 **미리 정의된 채점 로직**(에너지 방향 E/I · 판단 방식 L/F · 실행 방식 P/S, 3개 축의 조합)으로 즉시 결정되지만, 그 결과를 설명하는 코멘트는 **AI가 사용자의 실제 답변을 근거로 매번 새롭게 생성**합니다. 결과 화면에서 자기 유형에 대해 자유롭게 질문할 수 있는 대화형 기능도 함께 제공합니다.

**타겟 사용자**는 재미로 자기 이해를 하고 싶은 사람, 결과를 캡처해 공유하고 싶은 사람입니다.

## 2. 화면 구성

서비스는 하나의 페이지 안에서 화면을 전환하는 SPA 구조로, **홈 → 모드 선택 → 문제 풀이 → 결과** 순서로 이동합니다. 상단 로고를 클릭하면 언제든 홈으로 돌아갈 수 있습니다.

| 화면 | 설명 |
|---|---|

| 모드 선택 | 빠른 진단(5문항) / 정밀 진단(10문항) 중 선택 |

| 결과 | 카드 플립 연출로 유형 공개, AI 분석 4단락, 강점 태그, 궁합 유형, AI 추가 질문, 카드 다운로드 |

## 3. 기술 스택

| 영역 | 기술 | 핵심 책임 |
|---|---|---|
| HTML (`index.html`) | HTML5 | 화면 구조와 시맨틱 마크업, 4개 뷰(홈/모드선택/퀴즈/결과)의 뼈대 정의 |
| CSS (`css/style.css`) | CSS3 | 레이아웃·반응형 그리드·애니메이션 등 시각적 스타일 전담 |
| JS (`js/*.js`) | Vanilla JavaScript | 뷰 전환, 퀴즈 상태 관리, 채점 로직, `fetch`를 통한 API 호출과 DOM 갱신 |
| 백엔드 | Vercel Serverless Functions (Python) | AI API 호출을 대행해 API 키를 브라우저에 노출하지 않고 처리 |
| AI (주 provider) | Google Gemini API (`gemini-2.5-flash`) | 결과 분석 코멘트·질문 답변 생성 |
| AI (백업 provider) | Groq API (`llama-3.3-70b-versatile`) | Gemini 실패 시 자동 대체 |
| 기타 | html2canvas | 결과 카드 이미지 다운로드 |

> 프레임워크(React/Vue 등)는 사용하지 않았습니다. 이유와 향후 도입 시 고려사항은 [11장](#11-프레임워크-미사용-이유와-도입-시-고려사항)에 정리했습니다.

## 4. 아키텍처와 데이터 흐름

프로젝트는 **프론트엔드(`css/`, `js/`, `index.html`)와 백엔드(`api/`)가 폴더 단위로 명확히 분리**되어 있습니다. 이 분리 덕분에 API 키가 브라우저 코드에 절대 노출되지 않고, 프롬프트 튜닝이나 AI provider 교체 같은 백엔드 변경을 프론트엔드 코드와 독립적으로 수정·테스트할 수 있습니다.

```
.
├── index.html
├── css/style.css
├── js/
│   ├── types.js        # 8가지 유형 데이터
│   ├── questions.js     # 고정 질문 문항 (5/10문항)
│   └── app.js              # 뷰 전환·채점·fetch 호출·상태(state) 관리
├── api/
│   ├── analyze.py          # AI 기능 ① 결과 코멘트 생성
│   └── ask.py                # AI 기능 ② 추가 질문 답변
└── requirements.txt
```

`api/analyze.py`, `api/ask.py`는 반드시 저장소 최상위의 `api/` 폴더 바로 아래 위치해야 합니다. Vercel은 폴더 경로를 그대로 URL 경로로 매핑하므로, 위치가 어긋나면 해당 엔드포인트가 404로 처리됩니다.

### 프론트엔드 상태(state) 흐름

`js/app.js`의 `state` 객체가 현재 모드·답변·결과 유형을 관리하며, 화면은 다음 한 흐름으로 전환됩니다.

> 퀴즈 종료 → **로딩** 문구("AI가 카드를 그리는 중...") 노출 → API **성공** 시 결과 카드와 AI 코멘트로 즉시 교체 → API **실패** 시 토스트 안내와 함께 사전 정의된 정적 설명으로 자연스럽게 대체 (결과 화면 자체는 항상 정상 노출)

## 5. AI 기능 API 명세

### 5-1. `POST /api/analyze` — 결과 분석 코멘트

**요청 예시**
```json
{
  "typeName": "탐험가형",
  "typeCode": "EFS",
  "typeDesc": "당신은 호기심이 이끄는 대로 움직이는 자유로운 영혼이에요...",
  "answersText": "- 주말에 아무 계획이 없다면 당신은? → 친구들을 불러 모아 즉흥 모임을 만든다\n- ..."
}
```

**응답 예시 (성공, 200)**
```json
{
  "comment": "[오늘의 한마디]\n당신의 답변에서는...(중략)",
  "provider": "gemini"
}
```

**응답 예시 (실패, 예: 502)**
```json
{ "error": "Gemini API 오류: 429" }
```

### 5-2. `POST /api/ask` — AI에게 더 물어보기

이 엔드포인트는 서버에서 **빈 입력 / 정상 입력 / 최대 길이(200자) 초과 입력** 세 가지 케이스를 검증합니다. 실제 요청·응답 예시는 아래와 같습니다.

| 케이스 | 요청 예시 (`question` 필드) | 응답 |
|---|---|---|
| 정상 입력 | `"이 유형은 연애할 때 어떤 편이야?"` | `200` `{"answer": "...", "provider": "gemini"}` |
| 빈 입력 | `""` | `400` `{"error": "질문을 입력해주세요."}` |
| 200자 초과 입력 | 201자 이상의 긴 문자열 | `400` `{"error": "질문은 200자 이내로 입력해주세요."}` |

**공통 에러 코드 의미**

| 코드 | 의미 |
|---|---|
| `400` | 요청 값 검증 실패 (빈 입력, 길이 초과, 필수 필드 누락) |
| `500` | 서버에 `GEMINI_API_KEY`/`GROQ_API_KEY`가 설정되지 않음 |
| `502` | AI API 호출은 되었으나 응답 해석 실패, 또는 AI API 자체 오류 |
| `504` | AI 응답 지연(타임아웃, 12초 기준) |

## 6. 실패 처리 및 재시도 정책

- **빈 입력**: 질문 미선택/미입력 시 다음 단계 진행을 막고 인라인 경고 메시지를 표시합니다.
- **API 오류(4xx/5xx)**: Gemini 실패 시 Groq으로 자동 전환하고, 그래도 실패하면 토스트로 안내한 뒤 정적 설명으로 대체합니다.
- **지연/타임아웃**: 프론트엔드에서 15초, 백엔드에서 12초 기준으로 요청을 중단합니다.
- **네트워크 재시도 정책**: 현재는 실패 시 자동 재시도를 하지 않고, 사용자가 직접 다시 시도하도록 안내합니다("AI에게 더 물어보기"는 같은 버튼을 다시 누르면 재요청). 다건 요청이 몰릴 가능성이 있는 환경으로 확장할 경우, 짧은 지수 백오프(exponential backoff)로 1~2회 자동 재시도를 추가하는 것을 권장합니다.
- **접근성**: 현재 안내 메시지(토스트, 인라인 경고)는 시각적 텍스트로만 제공되며, 스크린리더를 위한 `aria-live` 속성 등은 아직 적용되어 있지 않습니다. 이는 [15장 향후 보완 사항](#15-향후-보완할-사항)에 포함되어 있습니다.

## 7. AI provider 이중화 (Gemini → Groq)

```
Gemini 호출 시도
  ├─ 성공 → 그대로 응답 반환
  └─ 실패 (할당량 초과 429, 타임아웃 등)
        └─ GROQ_API_KEY가 설정되어 있으면 Groq으로 자동 재시도
              ├─ 성공 → Groq이 생성한 응답 반환
              └─ 실패 → 프론트엔드가 기본 유형 설명으로 자연스럽게 대체
```

**우선순위 정책**: Gemini를 항상 먼저 시도합니다. Gemini가 한국어 표현과 지시사항 준수 품질이 더 좋다고 판단해 기본(primary)으로 두었고, Groq은 Gemini가 실패했을 때만 호출되는 백업(secondary) 역할입니다. 두 provider를 동시에 호출하거나 부하를 분산하는 방식은 사용하지 않습니다.

**예상 할당량(무료 티어 기준, 변동될 수 있음)**

| Provider | 분당 요청(RPM) | 하루 요청(RPD) |
|---|---|---|
| Gemini (`gemini-2.5-flash`) | 약 10~20회 | 약 250회 (모델·정책에 따라 더 낮아질 수 있음) |
| Groq (`llama-3.3-70b-versatile`) | 약 30회 | 최대 14,400회 |

이 프로젝트 규모(테스트 1회당 API 호출 1~2건)에서는 Gemini 단독으로도 개인 사용에 충분하지만, 여러 명이 동시에 시연·평가하는 상황을 대비해 Groq을 백업으로 구성했습니다. 정확한 최신 한도는 각 사의 공식 문서를 참고하는 것을 권장합니다.

**프롬프트 파라미터 변경 시 영향**

| 파라미터 | 값을 올리면 | 값을 내리면 |
|---|---|---|
| `temperature` | 표현이 다양해지지만 일관성·예측 가능성 감소 | 표현이 단조로워지지만 안정적인 톤 유지 |
| `maxOutputTokens` | 응답이 잘릴 위험 감소 | 실제로 겪었던 문제처럼 응답이 중간에 잘릴 수 있음 |
| `thinkingConfig.thinkingBudget` (Gemini 전용) | 내부 사고 단계를 늘리면 복잡한 추론 품질 향상 가능 | `0`으로 두면 사고 단계를 생략해 응답 속도는 빨라지지만, 복잡한 요청에서는 품질이 다소 낮아질 수 있음 (현재 이 프로젝트는 짧은 감성 코멘트 생성이 목적이라 `0`으로 설정) |

## 8. 실행 및 배포 방법

### 로컬 실행

```bash
# 의존성 설치
npm install -g vercel
pip install -r requirements.txt

# 환경 변수 설정
cp .env.example .env
# .env 파일을 열어 GEMINI_API_KEY(필수), GROQ_API_KEY(선택) 입력

# 로컬 개발 서버 실행 (정적 파일 + api/ 를 함께 서빙)
vercel dev
```

정적 파일(`index.html`)만 브라우저로 직접 열면 화면 확인은 가능하지만, `/api`를 서빙해줄 서버가 없어 AI 기능은 항상 대체 콘텐츠로 처리됩니다. AI 기능까지 확인하려면 `vercel dev` 또는 실제 배포가 필요합니다.

### 배포

1. 저장소를 GitHub에 push합니다. (최상위에 `index.html`, `css/`, `js/`, `api/`가 바로 보이는 구조여야 합니다.)
2. Vercel에 GitHub 계정으로 로그인 후 **Add New → Project**로 저장소를 import합니다.
3. Build 설정은 기본값 그대로 두고, **Deploy 전에** 환경 변수를 먼저 등록합니다.
4. Deploy를 진행하면 1~2분 뒤 배포 URL이 발급됩니다.
5. 이후 코드를 수정하고 `git push`하면 Vercel이 자동으로 재배포합니다.

| `GROQ_API_KEY` | 선택 | Gemini 호출 실패 시 자동 전환되는 백업 provider | [Groq Console](https://console.groq.com/keys) |

**환경별 설정 예시**
- **로컬**: 프로젝트 루트의 `.env` 파일에 `GEMINI_API_KEY=발급받은키` 형태로 저장 (`.gitignore`로 커밋에서 자동 제외됨)
- **Vercel (프로덕션/프리뷰)**: `.env` 파일을 사용하지 않고, 대시보드의 **Settings → Environment Variables**에 Key/Value로 직접 등록. 로컬 `.env`와 Vercel 값은 서로 다른 저장소이므로, 로컬에서만 키를 넣고 Vercel에 등록하지 않으면 배포 환경에서는 AI 기능이 동작하지 않습니다. 환경 변수를 새로 추가·수정한 뒤에는 반드시 **Redeploy**를 실행해야 반영됩니다.

## 10. 배포 진단 — 로그/콘솔 확인 방법

AI 기능이 배포 환경에서만 실패하는 경우, 브라우저 콘솔보다 **Vercel 함수 로그**를 확인하는 것이 원인 파악에 더 정확합니다.

1. Vercel 대시보드 → 해당 프로젝트 → 상단 **Logs** 탭(또는 Deployments → 특정 배포 클릭 → **Functions** 탭)으로 이동합니다.
2. 문제가 발생한 시점 전후로 `/api/analyze` 또는 `/api/ask` 호출 로그를 찾습니다.
3. 로그 항목에서 다음을 확인합니다.
   - **Status**: `404`면 파일 경로 문제(예: `api` 폴더 누락), `500`이면 환경변수 미설정, `502`/`504`면 AI API 자체의 오류·지연
   - **External APIs**: Gemini/Groq으로 실제 요청이 나갔는지 여부 (안 나갔다면 라우팅 단계에서부터 실패한 것)
   - **Execution Duration**: 비정상적으로 짧다면(예: 100ms 이하) 코드가 AI 호출 전에 조기 종료됐을 가능성이 높음

브라우저 쪽에서는 개발자도구(F12) → **Network** 탭에서 해당 요청의 응답 코드와 본문(JSON의 `error` 필드)을 먼저 확인하고, 더 구체적인 원인은 위 Vercel 로그에서 교차 확인하는 순서를 권장합니다.

## 11. 프레임워크 미사용 이유와 도입 시 고려사항

미션 요구사항상 프론트엔드는 바닐라 HTML/CSS/JS로 구현해야 하므로 React/Vue 등은 사용하지 않았습니다. 다만 향후 서비스가 커질 경우를 대비해 프레임워크 도입 시의 장단점을 정리하면 다음과 같습니다.

| 항목 | 현재 (바닐라 JS) | React/Vue 등 도입 시 |
|---|---|---|
| 초기 학습·설정 비용 | 낮음 (빌드 도구 불필요, 파일 열면 바로 실행) | 높음 (빌드 파이프라인, 생태계 학습 필요) |
| 상태 관리 | `state` 객체 + 수동 DOM 갱신 (`app.js`에서 직접 `textContent`/`innerHTML` 조작) | 선언적 상태 관리(Hooks 등)로 화면-상태 동기화 코드가 크게 줄어듦 |
| 번들 크기·초기 로딩 | 매우 가벼움, 별도 번들링 없이 즉시 로드 | 프레임워크 런타임만큼 번들 크기 증가, 빌드 단계 필요 |
| 화면(뷰)이 늘어날 때 유지보수성 | 뷰가 많아질수록 DOM 조작 코드가 반복·증가 | 컴포넌트 단위 재사용으로 장기적으로 유지보수 유리 |
| 예상 리팩터 비용(전환 시) | — | 현재 4개 뷰의 전환·렌더링 로직을 컴포넌트 단위로 전면 재작성 필요, 중~대 규모 공수 예상 |

현재 규모(4개 화면, 단순한 상태 전이)에서는 바닐라 JS로도 충분히 관리 가능하다고 판단해 프레임워크를 도입하지 않았습니다.

## 12. 확장성 및 향후 API 버전 관리

현재 `/api/analyze`, `/api/ask` 두 엔드포인트만 존재하며 버전 경로가 없습니다(`/api/v1/...` 형태 아님). 향후 응답 스키마를 크게 변경하거나 새로운 AI provider를 추가하는 등 하위 호환이 깨질 수 있는 변경을 할 경우, `/api/v2/analyze`처럼 버전을 경로에 명시해 기존 클라이언트(프론트엔드)가 깨지지 않도록 분리하는 것을 권장합니다. 필드를 추가하는 정도의 하위 호환 변경은 기존 필드를 유지한 채 새 필드만 덧붙이는 방식으로 처리합니다.

## 13. 보안 — API 키 유출 대응 절차

1. **즉시 폐기·재발급**: 키가 유출된 것으로 의심되면 해당 콘솔(Google AI Studio 또는 Groq Console)에서 즉시 키를 폐기하고 새 키를 발급합니다.
2. **임시 차단**: 재발급 전까지 서비스가 잘못된 키로 계속 호출되지 않도록, Vercel Environment Variables에서 해당 키 값을 잠시 비워두면 `500` 응답으로 AI 기능만 일시 비활성화되고 나머지 화면(퀴즈 진행 등)은 정상 동작합니다.
3. **팀·협업자 알림**: 함께 작업하는 사람이 있다면 키가 교체되었음을 즉시 공유해, 각자 로컬 `.env`도 새 키로 갱신하도록 합니다.
4. **커밋 이력 정리**: 만약 과거 커밋에 키 값이 그대로 남아있다면, 키 자체를 무효화하는 것이 최우선이며(1번), 이력을 완전히 지우고 싶다면 `git filter-repo` 또는 `git filter-branch`로 해당 커밋을 정리하고 강제 push합니다.

## 14. 개발 과정에서 겪은 문제와 해결

**저장소 구조 문제로 인한 CSS 미적용.** 저장소 안에 프로젝트 폴더가 한 단계 더 들어가 있는 구조라, Vercel이 최상위에 남아있던 예전 `index.html`을 그대로 읽어 CSS 경로가 깨진 상태로 배포되었습니다. 하위 폴더의 파일들을 저장소 최상위로 이동하고 중복 파일을 정리해 해결했습니다.

**`api` 폴더 위치로 인한 404 오류.** `analyze.py`가 `api` 폴더 없이 최상위에 놓여 있어, Vercel이 `/api/analyze` 경로 자체를 인식하지 못했습니다. `api/analyze.py` 경로로 정확히 재배치해 해결했습니다.

**AI 모델 지원 종료.** 코드에 명시했던 `gemini-2.0-flash` 모델의 API 지원이 종료된 상태였습니다. 현재 사용 가능한 `gemini-2.5-flash`로 모델명을 변경해 해결했습니다.

**AI 응답이 중간에 잘리는 문제.** `gemini-2.5-flash`가 답변 생성 전 내부 사고(thinking)에 토큰을 먼저 소비하는데, 응답 길이 한도(`maxOutputTokens`)가 낮게 설정되어 있어 실제 답변에 쓸 토큰이 거의 남지 않았습니다. `thinkingConfig.thinkingBudget: 0`으로 사고 단계를 생략하고 응답 한도를 상향해 해결했습니다.

**무료 할당량 소진 우려.** Gemini 무료 티어의 하루 요청 한도가 낮다는 점을 고려해, Gemini 호출이 실패하면 자동으로 Groq으로 전환되는 이중 구조를 추가했습니다.
